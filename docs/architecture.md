# Архитектура

protoledger — локальный инструмент исследования недокументированного бинарного протокола поверх TCP. Вход — записи трафика (pcap, pcapng) и журнал действий клиента; выход — проверяемое описание протокола, отчёт и команда повторного применения. Всё работает на одной машине, без сети и внешних сервисов.

## Компоненты

```
┌──────────── браузер на localhost ────────────┐
│ SPA (Nuxt): проект, обзор, исследование, проверка, отчёт │
└───────────────────────┬──────────────────────┘
        HTTP JSON /api/* · SSE (ход задач) · только 127.0.0.1
┌───────────────────────┴──────────────────────────────────────────┐
│ движок protoledger (Rust)                                         │
│  pl-server   HTTP, SSE, защита API, встроенная SPA                │
│  pl-app      сценарии: импорт, прогоны, реестр долгих задач       │
│  pl-capture · pl-reassembly · pl-actions · pl-interp · pl-verify · pl-report │
│  pl-project  папка проекта: единственный слой записи на диск      │
│  pl-core     общие типы и ошибки API                              │
└───────────────────────┬──────────────────────────────────────────┘
          <имя>.protoledger/ — текстовые YAML/JSON + неизменные копии записей
```

Один движок — две оболочки: `protoledger serve` (интерфейс в браузере) и командная строка (`apply`, `verify`, `report`). Интерфейс встроен в бинарник и использует только относительные адреса `/api`.

| Крейт | Отвечает за |
|---|---|
| `pl-capture` | Чтение pcap и pcapng, индекс кадров (смещения в файле, данные не копируются), разбор Ethernet/IPv4/TCP, диагностика всего, что вне этой области |
| `pl-reassembly` | Соединения с эпохами (повтор портов — новое соединение), роли, направленные потоки, карта участков `data`/`gap`/`ambiguous` с кадрами-источниками, политики перекрытий и контрольных сумм |
| `pl-actions` | Журнал действий (CSV): сопоставление колонок, время, параметры и наблюдаемый результат |
| `pl-interp` | Язык описания протокола (YAML): фрейминг, типы сообщений, поля со статусами знания, выражения; применение к потокам |
| `pl-verify` | Прогоны проверки на корпусе: категории результата, контрпримеры, сравнение прогонов, устаревание |
| `pl-report` | Отчёт Markdown и HTML |
| `pl-project` | Формат папки проекта, атомарная запись, манифест, источники, ревизии интерпретации, прогоны |
| `pl-app`, `pl-server` | Сценарии и HTTP API поверх библиотек |
| `pl-synth`, `pl-stand`, `pl-hostile` | Только тестовые данные: синтетические записи с дефектами захвата, стенд-устройство с журналом, «злые» файлы |

Зависимости — только сверху вниз. Библиотеки разбора, сборки и интерпретации не знают про HTTP, проект и интерфейс и проверяются тестами на синтетических и «злых» данных.

## Конвейер

```
запись ─► pl-capture ─► индекс кадров + диагностика ─► pl-reassembly ─► соединения, потоки, карта участков
поток ─► фрейминг ─► сообщения ─► обмены «запрос → ответ» ─► типы и поля ─► проверки и тесты гипотез
корпус ─► прогон ─► сводка по категориям + контрпримеры ─► сравнение с прошлым прогоном ─► отчёт
```

## Сборка TCP

| Ситуация | Поведение |
|---|---|
| Переупорядочивание | Сортировка по seq по модулю 2^32 (RFC 9293) |
| Одинаковый повтор | Байты учитываются один раз, все кадры-источники сохраняются с признаком повтора |
| Потеря, усечение при записи | Участок `gap` фиксированной длины; байты не подставляются |
| Перекрытие с разными байтами | Участок `ambiguous` со всеми вариантами; принятый вариант — по политике проекта (`first`, `last` или без выбора) |
| Нет SYN | Роли неизвестны, начало потока помечено как недоступное |
| Неверная контрольная сумма | Политика `ignore` / `warn` / `drop`; если все неверные суммы от одного узла — это, вероятно, offloading на нём |
| Повтор портов | Новое соединение по SYN с другим ISN или после FIN/RST |
| IPv6, фрагменты IPv4, не TCP, не Ethernet | Кадр пропускается с диагностикой, остальное работает |

Время результатов — время захвата кадров из записи.

## Статусы знания и категории результата

Поле описания протокола — `rule` (правило), `hypothesis` (гипотеза) или `unknown` (неизвестно). Гипотеза с тестом получает `supported k/n`, `refuted` (есть контрпример) или `untested`: совпадения не превращают её в доказанное правило.

Результат применения к сообщению:

| Категория | Когда |
|---|---|
| `matched` | Сообщение выделено, тип найден, поля разобраны, проверки прошли |
| `violated` | Нарушена проверка правила |
| `incomplete` | Сообщение задевает дыру или обрывается |
| `ambiguous` | Сообщение задевает неоднозначный участок |
| `unmatched` | Описание не охватывает такое сообщение |
| `out_of_scope` | Поток вне области описания |
| `unsupported` | Ограничение реализации, а не свойство протокола |
| `limit_exceeded` | Превышен защитный предел |

## Проект на диске

```
my-research.protoledger/
├─ project.yaml              версии формата и движка, настройки сборки, источники и журналы
├─ sources/<sha256>.<ext>    неизменные копии записей
├─ action-logs/              журналы действий
├─ interpretation/           текущее описание и все ревизии
├─ observations.yaml, hypotheses.yaml, questions.yaml
├─ runs/                     прогоны: входы (хеши), сводка, контрпримеры
├─ reports/
└─ .cache/                   пересобираемые индексы
```

Только относительные пути, запись атомарная. Результаты подписаны хешами входов, поэтому устаревшие отличимы от актуальных. Перенос проекта — копирование папки; `protoledger verify` подтверждает, что результаты воспроизводятся.

## Локальный API и безопасность

Движок слушает только `127.0.0.1` (в Docker порт публикуется только на `127.0.0.1` хоста). Каждый запрос к `/api` проверяется: заголовок `Host` и `Origin` — только свои, токен сессии `X-Protoledger-Token`, который движок отдаёт только своей странице. Ответы — с `Content-Security-Policy`, ошибки — Problem Details (RFC 9457). Записи и проекты считаются недоверенным вводом: ошибка разбора кадра — диагностика, а не падение; длины проверяются до выделения памяти; защитные пределы — в [limits.md](limits.md).

Контракт API — `openapi.yaml` и `API.md` в [репозитории движка](https://github.com/protoledger/protoledger-backend).
