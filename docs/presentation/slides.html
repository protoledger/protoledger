Проблема

Подключить систему к устройству без документации на протокол — обычная задача интеграции: контроллеры, измерительные приборы, IoT, устаревшие сервисы.

Сегодня это Wireshark, hex-редактор, заметки и одноразовые скрипты.

Что ломается

  • Выводы не привязаны к байтам конкретной записи
  • Догадка выглядит так же, как установленный факт
  • На новой записи всё проверяется заново руками
  • Коллеге передаётся результат, но не основания
  • Дефекты захвата (потери, повторы, offload) путают выводы
2

Решение: цикл исследования в одном инструменте

Записисборка TCP, дефекты явно
Исследованиеграницы, обмены, сравнение
Описаниеустановлено · предположение · не описано
Проверкавсе записи, расхождения
Передачаотчёт, YAML, папка проекта
3

Демо 1. Записи → описание протокола одной кнопкой11 записей «Термостенда» и журнал из 109 действий; колонки журнала и границы сообщений программа находит сама

Повторы, пропуски, обрезанные кадры и offload видны явно. «Составить описание»: сигнатура A6 5C, длина в байтах 2–3, код команды в байте 7, поля связаны с параметрами журнала: порог 19 °C → 07 6C = 1900.

4

Демо 2. Проверка на записях и на новой записи

Описание применяется ко всем записям: 200 сообщений, у полей — «совпало в 40 из 40». Запись, которой не было при составлении описания, разбирается без правки: 16 из 16.

5

Демо 3. Ошибка → расхождение → уточнение

Порог прочитан как число без знака: на пороге −2,5 °C байты FF 06 дают 65 286 вместо −250 — 2 расхождения с конкретными сообщениями.

«Как исправить»: читать как число со знаком — расхождений 0 вместо 2. Новая версия описания, проверка заново: совпало в 40 из 40.

Как это работает

SPA (Nuxt) — в браузере или окне Tauri │ HTTP JSON /api · SSE · только 127.0.0.1 │ Host/Origin + токен сессии движок protoledger (Rust, один бинарник) pl-server API, защита, встроенная SPA pl-app сценарии, реестр задач pl-capture pcap/pcapng → индекс кадров pl-reassembly TCP: потоки, дыры, перекрытия pl-actions журнал действий (CSV) pl-interp описание протокола, выражения pl-verify проверки, расхождения pl-report отчёт MD / HTML pl-project папка проекта, атомарная запись │ <имя>.protoledger/ YAML/JSON + копии записей

Один движок — три оболочки

Окно приложения (.msi, .deb, AppImage), браузер (docker compose up или бинарник serve), командная строка: apply, verify, report, draft.

Без базы данных

Состояние — папка проекта: текстовые YAML/JSON и неизменные копии записей с sha256. Перенос — копирование папки, protoledger verify воспроизводит проверки.

Достоверность и воспроизводимость

Знание со статусом

  • Поле — установлено, предположение или не описано
  • «Совпало в k из n», а не «доказано»
  • Каждый вывод — якорь на байты записи

Честные категории

  • Свойства протокола: нарушено, не охвачено
  • Дефекты записи: неполное, неоднозначное
  • Ограничения реализации: превышен предел, поток вне области

Воспроизводимо

  • Все версии описания хранятся
  • Проверка подписана хешами входов: устаревший виден
  • Детерминированный вывод: CLI ≡ интерфейс

Безопасность

  • Только 127.0.0.1, проверка Host и Origin, токен сессии, CSP
  • Без unsafe, без unwrap на данных

Злые входы

  • 93 «злых» файла в наборе, 5 целей фаззинга
  • Битый кадр — диагностика, а не падение

Проверки в CI

  • 419 тестов движка, fmt и clippy без предупреждений, аудит лицензий
  • 16 эталонов, демо по кнопкам в браузере

Ограничения и развитие

Сейчас — честно

  • Область ТЗ: Ethernet + IPv4 + TCP; IPv6, UDP и фрагменты IP — пропускаются с диагностикой
  • Шифрованный трафик не разбирается — показывается как неописанные байты
  • Запись читается в память целиком (предел 1 ГиБ)
  • Предположение не становится доказанным: проверено только на наблюдавшихся значениях
  • Установщики — Windows и Linux

Дальше

  • IPv6 и UDP — новые слои того же конвейера
  • Чтение записи частями для файлов больше памяти
  • Эксперименты со стендом из приложения: конструктор сообщений
  • Двойник устройства по выученным парам «запрос → ответ»
  • Экспорт парсера: Wireshark уже есть, далее Kaitai Struct
