Проблема

Подключить систему к устройству без документации на протокол — обычная задача интеграции: контроллеры, измерительные приборы, IoT, устаревшие сервисы.

Сегодня это Wireshark, hex-редактор, заметки и одноразовые скрипты.

Что ломается

  • Выводы не привязаны к байтам конкретной записи
  • Догадка выглядит так же, как установленный факт
  • На новой записи всё проверяется заново руками
  • Коллеге передаётся результат, но не основания
  • Дефекты захвата (потери, повторы, offload) путают выводы

Решение: цикл исследования в одном инструменте

Записисборка TCP, дефекты явно
Исследованиеграницы, обмены, сравнение
Описаниеправило · гипотеза · неизвестно
Проверкакорпус, контрпримеры
Передачаотчёт, YAML, папка проекта
3

Демо 1. Записи и потоки11 записей «Термостенда» и журнал из 109 действий; колонки журнала угадываются сами

Повторы не задваиваются, дыра остаётся дырой, перекрытие с разными байтами — «неоднозначно», частичная контрольная сумма распознана как offload. Каждый байт — с кадром и смещением.

4

Демо 2. Границы, обмены, связи с журналом

Поле длины u16 BE @2 +8 подтверждено на 100 % сообщений, сигнатура A6 5C. Для действия set-config c порогом 19 найдены запрос и ответ: 07 6C = 1900. Это подсказки с основаниями, а не выводы.

5

Демо 3. Ошибка → контрпример → уточнение

Порог прочитан как u16: 200 сообщений, гипотезы H6 и H12 опровергнуты на пороге −2,5 °C (65286 ≠ −250), со строкой журнала.

Исправлено на i16 — новая ревизия, прогон по всему корпусу: 216 сообщений, 0 контрпримеров; сравнение прогонов показывает, что изменилось.

Как это работает

SPA (Nuxt) — в браузере или окне Tauri │ HTTP JSON /api · SSE · только 127.0.0.1 │ Host/Origin + токен сессии движок protoledger (Rust, один бинарник) pl-server API, защита, встроенная SPA pl-app сценарии, реестр задач pl-capture pcap/pcapng → индекс кадров pl-reassembly TCP: потоки, дыры, перекрытия pl-actions журнал действий (CSV) pl-interp описание протокола, выражения pl-verify прогоны, контрпримеры pl-report отчёт MD / HTML pl-project папка проекта, атомарная запись │ <имя>.protoledger/ YAML/JSON + копии записей

Один движок — три оболочки

Окно приложения (.msi, .deb, AppImage), браузер (docker compose up или бинарник serve), командная строка: apply, verify, report, draft.

Без базы данных

Состояние — папка проекта: текстовые YAML/JSON и неизменные копии записей с sha256. Перенос — копирование папки, protoledger verify воспроизводит прогоны.

Достоверность и воспроизводимость

Знание со статусом

  • Поле — правило, гипотеза или неизвестно
  • Гипотеза — «поддержана k из n», не «доказана»
  • Каждый вывод — якорь на байты записи

Честные категории

  • Свойства протокола: нарушено, не охвачено
  • Дефекты записи: неполное, неоднозначное
  • Ограничения реализации: не поддержано, превышен предел

Воспроизводимо

  • Ревизии описания хранятся все
  • Прогон подписан хешами входов: устаревший виден
  • Детерминированный вывод: CLI ≡ интерфейс

Безопасность

  • Только 127.0.0.1, проверка Host и Origin, токен сессии, CSP
  • Без unsafe, без unwrap на данных

Злые входы

  • 93 «злых» файла в корпусе, 5 целей фаззинга
  • Битый кадр — диагностика, а не падение

Проверки в CI

  • 419 тестов движка, fmt и clippy без предупреждений, аудит лицензий
  • 16 эталонов, демо по кнопкам в браузере

Ограничения и развитие

Сейчас — честно

  • Область ТЗ: Ethernet + IPv4 + TCP; IPv6, UDP и фрагменты IP — пропускаются с диагностикой
  • Шифрованный трафик не разбирается — показывается как неописанные байты
  • Запись читается в память целиком (предел 1 ГиБ)
  • Гипотеза не становится доказанной: проверена только на наблюдавшихся значениях
  • Установщики — Windows и Linux

Дальше

  • IPv6 и UDP — новые слои того же конвейера
  • Чтение записи частями для файлов больше памяти
  • Эксперименты со стендом из приложения: конструктор сообщений
  • Двойник устройства по выученным парам «запрос → ответ»
  • Экспорт парсера: Wireshark уже есть, далее Kaitai Struct
