# Форматы

Все файлы продукта — текстовые (YAML и JSON), кроме неизменных копий записей. Их можно читать, сравнивать и хранить в системе контроля версий.

## Проект

Проект — папка с суффиксом `.protoledger`. Внутри только относительные пути, поэтому перенос на другую машину — это копирование папки.

```
my-research.protoledger/
├─ project.yaml                 манифест: версии, настройки сборки, записи, журналы, ревизии, прогоны
├─ sources/<sha256>.<pcap|pcapng>   неизменные копии записей, имя — хеш содержимого
├─ action-logs/<sha256>.csv     копии журналов действий
├─ interpretation/
│  ├─ current.yaml              текущее описание протокола
│  └─ history/0001.yaml …       все ревизии, не изменяются
├─ runs/run-0001.json …         прогоны проверки: входы, сводка, контрпримеры
├─ observations.yaml            наблюдения с якорями на байты
├─ hypotheses.yaml              гипотезы: утверждение, основания, тест, статус
├─ questions.yaml               открытые вопросы исследователя
└─ .cache/                      пересобираемые данные; копировать не обязательно
```

Запись в проект атомарная: временный файл в той же папке, затем переименование.

### `project.yaml`

```yaml
formatVersion: 1
engineVersion: "1.0.0"
name: demo
settings:
  overlapPolicy: first      # что брать при перекрытии с разными байтами: first, last, flag
  checksumPolicy: warn      # неверные контрольные суммы: ignore, warn, drop
imports:                    # каждый импорт — отдельная запись, повторный импорт не склеивается
  - id: imp-0001
    sha256: d05c6bf0…
    name: main.pcapng
    format: pcapng
    sizeBytes: 71288
interpretations:
  - rev: 1
    digest: 2ac26870…       # sha256 канонической формы описания
runs:
  - id: run-0001
actionLogs:
  - id: log-0001
    sha256: 2e5adbe5…
    name: main.actions.csv
    mapping: { time: time, action: action, params: params, result: result }
    rows: 16
```

Журнал, импортированный повторно — с другим сопоставлением колонок или с поправкой часов, — это новая запись `actionLogs` с тем же `sha256`; файл копии один. В анализе действует последняя запись файла, прежние остаются в манифесте: по ним воспроизводятся прогоны, выполненные до замены.

Проект с `formatVersion` новее, чем понимает движок, не открывается — с понятной ошибкой.

### Прогон `runs/run-NNNN.json`

Прогон подписан своими входами: ревизия и `digest` описания, хеш настроек сборки, хеши записей корпуса, фильтры корпуса, версия движка, хеши журналов действий. Если журнал к моменту прогона был разобран не с первым своим сопоставлением колонок, прогон запоминает и дайджест сопоставления (`logMappings`), — `protoledger verify` повторяет каждый прогон с тем сопоставлением, с которым он выполнен. Если что-то из этого изменилось, прогон остаётся читаемым, но помечается устаревшим с причиной. Внутри — сводка по всему корпусу, таблица сообщений по потокам и контрпримеры с якорями (запись, поток, диапазон байтов, sha256 байтов).

## Описание протокола (файл YAML)

Формат `protoledger/interpretation@1`, YAML. Якоря и ссылки YAML не допускаются, размер файла — до 4 МиБ. Пример целиком — [`examples/thermostand/interpretation.yaml`](../examples/thermostand/interpretation.yaml).

```yaml
format: protoledger/interpretation@1
scope:                          # к каким потокам применяется описание
  direction: any                # any, a_to_b, b_to_a
  filter: "dst_port == 46123 || src_port == 46123"
framing:                        # как поток делится на сообщения
  kind: length_prefixed
  length: { at: 2, type: u16be, adjust: 8 }   # длина сообщения = значение поля + adjust
  sync: "a65c"                  # сигнатура начала: по ней разбор продолжается после дыры
  status: rule
messages:
  - id: set_config_req
    when: "dir == 0 && cmd == 0x20"   # условие, по которому узнаётся тип сообщения
    fields:
      - { name: signature, at: 0, type: bytes, len: 2, expect: "a65c", status: rule }
      - { name: length, at: 2, type: u16be, status: rule }
      - { name: period_ms, at: 9, type: u16be, status: hypothesis, hypothesis: H5 }
      - { name: label_len, at: 13, type: u8, status: hypothesis, hypothesis: H7 }
      - { name: label, at: 14, type: string, len: "label_len", status: hypothesis, hypothesis: H7 }
hypotheses:
  - { id: H5, statement: "period_ms — период измерений в миллисекундах", test: "period_ms == action.params.period_ms" }
checks:
  - { id: C1, kind: structural, expr: "length + 8 == message.len", description: "длина в заголовке не совпадает с размером сообщения" }
```

### Фрейминг

| `kind` | Параметры | Смысл |
|---|---|---|
| `length_prefixed` | `length: {at, type, adjust}`, необязательно `sync` | Длина в заголовке сообщения. `type: varint` — число переменного размера (по 7 бит в байте, младшие первыми, как в MQTT): размер сообщения считается от конца самого поля длины |
| `fixed` | `size` | Сообщения одного размера |
| `delimiter` | `bytes` (hex) | Сообщение кончается разделителем |
| `magic` | `bytes` (hex) | Сообщение начинается сигнатурой |

### Поля

| Свойство | Значения |
|---|---|
| `at` | Смещение от начала сообщения, `end-N` — от конца, `next` — сразу за предыдущим полем описания (для полей после строки или числа переменного размера) |
| `type` | Целые: `u8`, `i8`, `u16be`, `u16le`, `i16be`, `i16le`, `u32be`, `u32le`, `i32be`, `i32le`, `u64be`, `u64le`, `i64be`, `i64le`. С плавающей точкой: `f32be`, `f32le`, `f64be`, `f64le` — значение читается кратчайшей десятичной записью (`21.3`), с журналом сравнивается через `dec(x, n)`. `bcd` — двоично-десятичное число, `len` от 1 до 8 байт. `varint` — целое переменного размера, по 7 бит в байте, младшие первыми. `bytes`, `string`, `unknown` |
| `mask` | У целого поля — битовое поле: значение — биты маски, сдвинутые к младшему (`mask: 0x38` даёт число от 0 до 7); несколько полей могут делить один байт |
| `len` | Для `bytes`, `string`, `unknown`: число, `to_end` или выражение по ранее объявленным полям |
| `expect` | Ожидаемое значение: число или hex-строка |
| `status` | `rule` — получено по правилу, `hypothesis` — предположение о назначении, `unknown` — зона, смысл которой неизвестен |
| `hypothesis` | Идентификатор гипотезы, на которую опирается поле |
| `repeat` | Повторяющаяся группа: `count` (число или выражение) и `fields`; поля элемента называются `<группа>.<номер>.<поле>` |

Байты сообщения, не покрытые полями или попавшие в `unknown`, считаются отдельно: частичное описание — нормальное состояние, а не ошибка.

### Выражения

Используются в `when`, `checks`, `len`, `repeat.count` и в тестах гипотез. Собственный интерпретатор: без доступа к файлам, сети и процессам, до 10 тыс. шагов и 32 уровней вложенности.

- Операции: `||`, `&&`, `!`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `+`, `-`, `*`, `/`, `%`, скобки; числа десятичные и `0x…`, строки в кавычках.
- Имена: поля сообщения, `message.len`, `message.start`; в условии области и в `when` — `src_port`, `dst_port`, `src_ip`, `dst_ip` (так различают запрос и ответ, когда в байтах направления нет).
- В тестах гипотез дополнительно: `response.<поле>` — поле парного ответа; `action.name`, `action.params.<имя>`, `action.result.<имя>` — действие из журнала.
- Контрольные суммы байтов сообщения `[от, до)`, все вида `имя(от, до)`: `sum8`, `sum16`, `lrc8`, `xor8`, `fletcher16`, `inet16` (RFC 1071), `crc8`, `crc8_maxim`, `crc16_modbus`, `crc16_arc`, `crc16_usb`, `crc16_ccitt`, `crc16_xmodem`, `crc16_kermit`, `crc16_x25`, `crc16_dnp`, `crc32`, `crc32c`, `crc32_bzip2`, `crc32_mpeg2`. Пример проверки: `crc == crc16_modbus(0, message.len - 2)`.
- `dec(x, n)` — десятичное число из журнала как целое с `n` знаками после запятой (`dec("-2.5", 2)` = −250).

Неизвестное имя — отдельный исход «неприменимо», а не ноль: тест, для которого в сообщении нет нужных данных, гипотезу не подтверждает и не опровергает.

### Результат гипотезы

Гипотеза с тестом получает один из итогов: «контрпримеров нет» (выполнилась на k из n применимых примеров), «опровергнута» (есть контрпример с якорем) или «не проверена» (применимых примеров нет). Совпадение на примерах не превращает гипотезу в доказанное правило.

## Журнал действий

CSV с произвольными именами колонок. Сопоставление колонок — YAML или JSON:

```yaml
time: start_utc          # колонка времени
action: action           # колонка имени действия
params: parameters       # необязательно
result: observed_result  # необязательно
paramsFormat: json       # kv (ключ=значение;…) или json
resultFormat: json
timeFormat: rfc3339      # rfc3339, unix_seconds, unix_millis, unix_micros, unix_nanos
utcOffsetMinutes: 0      # пояс для времени без пояса
clockOffsetMs: 0         # поправка на сдвиг часов клиента относительно часов записи
source: capture          # необязательно: колонка с именем записи, если журнал один на несколько записей
```

Вложенный JSON разворачивается в имена через точку (`configuration.period_ms`, `measurements.0.temperature_c`). Строки, которые не разобрались, не теряются молча: они перечислены с причиной, а журнал, где разобрано меньше половины строк, отклоняется.

## Результат `protoledger apply`

JSON, формат `protoledger/apply-result@1`: политика сборки, `digest` описания, по каждой записи — sha256, число кадров и соединений, диагностика захвата, по каждому потоку — сообщения с категорией, типом, значениями полей и нарушениями; итоги гипотез. Времени выполнения в результате нет, поэтому повторный запуск даёт тот же файл байт в байт. Примеры — `examples/*/expected/`.
