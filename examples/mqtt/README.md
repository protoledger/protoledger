# mqtt — протокол с длиной переменного размера

MQTT 3.1.1 — открытый протокол обмена сообщениями (спецификация OASIS). Пример проверяет подход на протоколе, устроенном иначе, чем «Термостенд» и Modbus: длина пакета — число переменного размера, тип пакета занимает половину байта, а место полей зависит от длины строк перед ними. В коде движка о MQTT нет ни строки — всё описание лежит в `interpretation.yaml`.

| Файл | Что внутри |
|---|---|
| `session.pcap` | Сеанс клиента с брокером на порту 1883: подключение, две подписки, публикации без подтверждения и с подтверждением, длинная публикация (длина пакета занимает два байта, пакет приходит двумя сегментами), команда от брокера, проверка связи, отключение |
| `actions.csv`, `mapping.yaml` | Журнал действий клиента (15 действий): время, действие, параметры и результат в JSON |
| `interpretation.yaml` | Описание протокола: фрейминг, 8 видов пакетов, 11 гипотез, из них 8 с тестами по журналу и парному ответу |
| `expected/apply-session.json` | Результат `protoledger apply` |
| `generate.mjs` | Генератор записи и журнала: кадры собираются по спецификации, сеть и брокер не нужны |

## Ход исследования

| Шаг | Что показал движок | Что решил исследователь |
|---|---|---|
| Границы | Кандидат — длина `u8` по смещению 1, размер = значение + 2: 22 сообщения, покрыто 92,7 % байтов, есть контрпример — пакет, где байт длины равен `D0`, а пакет длиннее | Старший бит байта длины — признак продолжения: длина переменного размера (`type: varint`). С таким фреймингом разбираются все 25 пакетов |
| Типы | По целому первому байту типы не выделились: значений много для 25 пакетов | Тип — старшие четыре бита первого байта, младшие — флаги: поля с `mask` |
| Строки | В запросах клиента — длина и текст сразу за ней, пример «MQTT» | Строки идут с длиной `u16`; поля после строки описаны как `at: next` — сразу за предыдущим |
| Связи с журналом | Тема и данные публикации, идентификатор клиента, интервал проверки связи совпадают с параметрами действий | Гипотезы с тестами `topic == action.params.topic`, `payload == action.params.value` и другие |

## Сверка со спецификацией

| Поле описания | Гипотеза, проверенная на записи | В спецификации |
|---|---|---|
| `type`, `qos` | H1, H2: старшие четыре бита и биты 1–2 первого байта | MQTT Control Packet type; QoS level в флагах PUBLISH |
| `remaining` | число байт после поля длины, по 7 бит в байте | Remaining Length, Variable Byte Integer |
| `protocol`, `level` | H3: «MQTT», 4 | Protocol Name, Protocol Level 4 (версия 3.1.1) |
| `keepalive`, `client_id` | H4, H5: совпадают с параметрами подключения | Keep Alive, Client Identifier |
| `return_code` | H6: 0 при успешном подключении | Connect Return code: 0 — Connection Accepted |
| `topic`, `payload` | H7, H8: совпадают с темой и значением из журнала | Topic Name, Application Message |
| `packet_id` | H9: подтверждение повторяет номер запроса | Packet Identifier; есть у PUBLISH только при QoS > 0 |
| `filter`, `requested_qos`, `granted_qos` | H10, H11 | Topic Filter, Requested QoS, SUBACK Return Code |

Тесты всех гипотез выполняются без контрпримеров. Это совпадение на примерах: H9 проверена только на подписках — у публикаций с подтверждением перед ответом брокера стоят публикации без ответа, пара запрос→ответ неоднозначна, и движок её не додумывает.

Не описаны намеренно: флаги подключения и признак сохранённого сеанса — по одному байту, помечены `unknown`.

## Повторить

```bash
protoledger apply --interpretation examples/mqtt/interpretation.yaml \
  --input examples/mqtt/session.pcap \
  --action-log examples/mqtt/actions.csv --mapping examples/mqtt/mapping.yaml \
  > /tmp/apply-session.json
diff /tmp/apply-session.json examples/mqtt/expected/apply-session.json && echo совпало

node examples/mqtt/generate.mjs    # пересоздать запись и журнал: файлы не меняются
```
